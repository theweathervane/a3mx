## The camera limits

Every stage has the same limits: the fighters' layer scrolls with the screen's left edge from **256**
to **640**, so every stage is **768** wide (fighters stay between 280 and 1000). The limits are not
in the stage data: stage set-up (0x0881ECA4) gives a layer in camera mode 1 the constants 0x100 and
0x280, and every stage's fighters' layer is in mode 1. The other layers have no limits (-1): they
scroll at their own rate as the camera moves (parallax).

| Address | What |
|---|---|
| 0x092E88A0 | the fighters' layer (layers are 0xA0 bytes apart from 0x092E8800): +2 camera mode, +34 camera x (s16, screen left, also as 16.16 at +32), +68 left limit, +70 right limit |
| 0x092E1228 | s16: the stage being fought on |
| 0x08E759D1 | s8: the STAGE row's choice on the select screen (0 RANDOM, 1-38 as in the table) |
| 0x08A2B3E6 | u8[64]: choice - 1 -> stage number; RANDOM picks entry `rand & 63` (the 38 stages then a second run of the main ones, so the BATTLE stages and the second versions come up less often) |

| 0x089F3200 | char *[42]: stage number -> archive name (`st00.pac` ... `st29.pac`) |
| 0x08A0F718 | char *[42]: the name of each slot (RYU ... INGRID), same numbering; 0x08A120DC is the Japanese spelling (GOUKI, NASH, ...) |

### The four stage numbers you can't pick

Stage numbers run 0x00 - 0x29, which is 42, but the disc has only the 38 archives above. The other
four numbers are not missing stages: the archive table points each one at a stage that already
exists, and the name table gives the slot a name. None of them appears among the 64 entries of the
select screen's table (0x08A2B3E6), so FREE BATTLE never reaches them, RANDOM included.

| Stage | Slot name | Loads | Which is the stage of |
|---|---|---|---|
| 0x12 | CHUN-LI | st04.pac | CHUNLI (0x04) |
| 0x13 | GEN | st11.pac | GEN (0x11) |
| 0x14 | SODOM | st06.pac | SODOM (0x06) |
| 0x1F | JUNI | st1e.pac | BISON2 (0x1E, whose slot is JULI) |

For 0x00 - 0x24 the stage number is the character number of the stage's owner (0x17 is E.RYU, so RYU
2 is Evil Ryu's stage; 0x24 is S.AKUMA, so AKUMA 2 is Shin Akuma's). 0x12 - 0x14 are second CHUN-LI,
GEN and SODOM slots, and JUNI shares JULI's stage. From 0x25 on the numbers stop matching:
the character slots 0x25 - 0x29 are BALROG, EAGLE, MAKI, YUN and INGRID, while the stages are BATTLE1
- 4 and KARIN 2.

## Stage objects

Besides its tile layers, every stage but BATTLE1 - 4 has a few **objects**: the pieces that move or
animate on their own, drawn as sprites. Ryu's straw and rocks, Ken's crowd, Chun-Li's spectators, Guile's
helicopter and trees, Bison's storm and leaves, Balrog's casino girls, Fei Long's crowd, Honda's figure
and the like. Each stage has a list of 16-byte records in the program (table 0x08A143D8 by stage number)
that says which objects to make, of which kind and type, where (x, y), in which sprite layer and how
they follow the camera; each kind has its own routine (table 0x08A101F0) and its own animations.
All of it is native C since 0.89.0 (`src/core/stage/objects.c`; the record format and the kinds are in
[PSP_PROGRAM_MAP.md](PSP_PROGRAM_MAP.md#the-stages-objects-decompiled-srccorestageobjectsc)).

`python tools/stage_objects.py` lists every stage's records (`--stage 0x00` for one, `--markdown` for a
table, `--json` for tools). For example RYU 1:

```
0x00 RYU: 4 objects
   kind  0 (0x0884B034) type  1  x   256 y    0  layer 0 camera 2  ...
   kind  1 (0x0884B1C4) type  3  x   976 y   48  layer 1 camera 2  ...
   kind  0 (0x0884B034) type  2  x   792 y  176  layer 1 camera 2  ...
   kind  2 (0x0884B2AC) type  0  x   -16 y   80  layer 1 camera 0  ...
```

The objects are not tile layers, so WIDE NATIVE's stage extensions (one strip per layer,
[STAGE_EXTENSIONS.md](STAGE_EXTENSIONS.md)) can't cover them: where an object's art reaches the 4:3 edge
it is cut there (RYU 1's straw on the left, Guile's trees, Blanka's palm, Mika's ropes, Adon's leaves,
Charlie's plane, Sagat's lily pads, Karin 1's boat...). Widening them is future work, now that their
code is native: per-object art, or more objects at the edges, in WIDE NATIVE only.

### What is drawn in front of the fighters

Measured on every stage in the fight (0.90.0): no tile layer and no floor band is in front of the
fighters. The layers draw at depths 5, 9 and 13 and the floor at 13, the fighters at 16 (the 2D
library draws a larger depth in front, and equal depths in the order they were queued). The only stage
art in front of them is **objects in sprite layer 0 at depth 16** (record layer 0, +24 = 7), queued
after the fighters:

| Stage | Objects in front (record index: kind, type, camera, x, y) |
|---|---|
| 0x00 RYU | #0: kind 0 type 1, camera 2, x 256 y 0 (the straw, bottom left) |
| 0x05 ADON | #0: kind 11 type 4, camera 2, x 320 y 32; #1: kind 10 type 1, camera 2, x 624 y 24 |
| 0x06 SODOM, 0x14 SODOM (2) | #0: kind 15 type 2, camera 2, x 1232 y 48 |
| 0x07 GUY | #0: kind 16 type 0, camera 2, x 288 y 0 |
| 0x0B SAGAT | #0 - #4: kinds 28 / 29 (types 9, 7, 9, 2, 0), camera 2, along the bottom (x 320 - 704) |
| 0x0C DAN | #0: kind 30 type 0, camera 2, x 282 y 0 |
| 0x0E ROLENTO | #0 - #4: kind 35 (types 1, 2, 3, 0, 0), camera 0, y 26 (the pieces along the bottom) |
| 0x1B CODY | #0 - #2: kind 60 (types 4, 5, 6), camera 2, x 448 / 616 / 880 |
| 0x20 GUILE | #3: kind 73 type 5, camera 0, x 512 y 0 |
| 0x23 HAWK | #2: kind 78 type 3, x 736 y 16; #4: kind 78 type 6, x 144 y 16 (camera 2) |

Every other stage object is behind the fighters (sprite layers 1 - 3, or depth 12 and less). Like all
objects these are cut at the 4:3 edge in WIDE NATIVE; the layer strips don't reach them, so since 0.92.0 each has its own placeholder pieces pinned to it ([STAGE_EXTENSIONS.md](STAGE_EXTENSIONS.md#foreground-objects-0920)).

## Widescreen

WIDE NATIVE shows 480 pixels instead of 384, 48 more on each side: at the limits the view spans 208 -
1072 instead of 256 - 1024. Where a stage's art stops short of that, the edge is black (KNOWN_ISSUES
M7). The last two columns are that black strip at each edge with the camera at its limit, in pixels
(0 - 48): the widest (the layer whose art is shortest) and the narrowest (often 0 where the floor or a
foreground layer covers the edge).

- **No black edges:** GUILE and BATTLE1 - 4; FEILONG on the right.
- **Nearly none:** MIKA (10 px), ZANGIEF (14 px), BIRDIE on the right and KARIN 1 on the left (16 px).
- **About a full strip (up to 48 px):** ADON, SODOM, ROLENTO, CAMMY, HONDA, DEEJAY, and one side of
  several more.

**Decided: extend the art and keep the limits.** The limits also set where the walls are: fighters
stay 24 px inside the 4:3 view, between 280 and 1000. Pulling the limits in would make the stage
narrower and move the corners, which changes how fights play and breaks the WIDE NATIVE parity rule.
Instead, every stage gets a **stage extension**, a strip per side for each layer (48 × 288; the placeholders are 64 wide since 0.90.0, reaching 8 columns under the layer's own art and 8 past the screen's edge). The game will draw it
behind the stage's art, only in WIDE NATIVE, so NORMAL and WIDE are untouched. Magenta placeholders
are committed in `assets/extensions/stages/<number>_<name>/`, ready to be painted. The size, placement, painting
notes and a per-stage table of what each strip shows are in
[STAGE_EXTENSIONS.md](STAGE_EXTENSIONS.md).

The table above counts the screen's rows 60 - 229 with the fighters on the ground. STAGE_EXTENSIONS.md
measures all 288 rows the strip covers, camera raised as well. So some stages that show 0 here
(GUILE, BATTLE1 - 4) still need a strip: below the floor's art, and at the top mid-jump.

More on what works and what doesn't in widescreen, and what a revision must keep: [WIDESCREEN.md](WIDESCREEN.md).
